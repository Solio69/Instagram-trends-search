# Implementation Plan: Разбор ниши

**Branch**: `003-niche-normalization` | **Date**: 2026-10-29 | **Spec**: [spec.md](./spec.md)

## Summary

Один серверный Route Handler принимает описание ниши, вызывает бесплатную модель OpenRouter и возвращает проверенные группы поисковых слов. Клиентская форма показывает загрузку, затем реальные группы в существующем блоке либо ошибку. Снимок Apify не отображается после отправки произвольной ниши.

## Technical Context

**Stack**: Next.js 16.4.3, React 19.3.1, TypeScript 7, SCSS Modules  
**Model**: `nvidia/nemotron-3.5-super-vl:free` через OpenRouter Chat Completions  
**API**: `POST /api/niche/normalize`  
**Dependencies**: новых пакетов нет; используются `fetch`, `Response` и встроенная поддержка `.env.local` в Next.js  
**Tests**: `node --experimental-strip-types --test tests/*.test.mjs`; `npm run build`  
**Live check**: два запроса к модели при наличии `OPENROUTER_API_KEY`

## Constitution Check

Конституция проекта остаётся шаблоном с плейсхолдерами, как и в предыдущей UI-задаче. Применяются [AGENTS.md](../../AGENTS.md), согласованная спецификация и тестовый цикл Red → Green. Текущая задача не вводит новые правила проекта.

## Design

1. `app/lib/niche-normalization.ts`: тип ответа, JSON Schema для OpenRouter, системная инструкция, проверка входа и ответа, вызов модели с внедряемым `fetch` для тестов.
2. `app/api/niche/normalize/route.ts`: тонкий серверный HTTP-слой; читает ключ из `process.env`, ограничивает вход, вызывает модуль и возвращает безопасные ошибки. В ответе нет ключа и сырых ошибок провайдера.
3. `TrendExplorer`: состояние текущего запроса, загрузки, результата и ошибки; результат предыдущего ввода сбрасывается при изменении текста. Демонстрационная таблица временно не выводится в живом сценарии.
4. `SearchPanel` и `FormalizationPanel`: получают проверенные данные через props. Формат публикаций отображается как настройка формы; языки и описания тем не придумываются. Карточки показывают метку направления и поисковые слова.

Системная инструкция задаёт разницу между широким зонтичным понятием и узким запросом на двух согласованных примерах. Схема содержит только `intent` и `topics[{name,terms[]}]`; модель не составляет финальный синтаксис Apify. Сервер проверяет количество и длину строк, пустые значения и повторы. Эта проверка не доказывает семантическую правильность расширения; её оценивает live-проба.

## Error handling and security

- Пустой или слишком длинный ввод: 400.
- Нет ключа: 503 с понятным сообщением, без демо-подстановки.
- Ошибка, лимит или тайм-аут OpenRouter: безопасный 502/429.
- Некорректный JSON или структура: 502.
- Ключ только в серверном окружении, без `NEXT_PUBLIC_` и без логирования.

## Test-first and verification plan

1. Написать тесты входа, проверки ответа и вызова модели с подставным `fetch`; убедиться в ожидаемом Red.
2. Реализовать серверный модуль и Route Handler, добиться Green.
3. Подключить UI к API и проверить сборкой. Проверить, что старые данные Apify не появляются как результат нового ввода.
4. При наличии ключа отправить «healthy» и «фитнес и тренировки», сверить смысл групп и зафиксировать фактические ответы без секрета.
5. Записать команды и результаты в `verification.md`, просмотреть diff и отсутствие секрета.
