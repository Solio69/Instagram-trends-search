# Feature Specification: Разбор ниши

**Feature Branch**: `003-niche-normalization`  
**Created**: 2026-10-29  
**Status**: Согласовано  
**Input**: Подключить бесплатную модель через OpenRouter для разбора введённой ниши и показать полученные поисковые слова в существующем блоке.

## Agreed scope and decision boundaries

Результат: после отправки непустого описания ниши блок разбора показывает группы поисковых слов, полученные для этого текста через OpenRouter. Широкий запрос может раскрываться на входящие направления; узкий остаётся в своих границах. Например, «healthy» охватывает фитнес, питание и ЗОЖ/wellness, а «фитнес и тренировки» не добавляет питание. Названия групп — краткие метки, описания тем не генерируются.

В объёме: серверный вызов бесплатной модели, проверка структуры её ответа, состояния загрузки и ошибки, подстановка реальных групп в существующий блок. Ключ доступа хранится только на сервере. Вне объёма: вызов Apify, сохранение в Postgres, поиск и ранжирование публикаций, изменение настроек формы и реализация редактирования разбора пользователем. Демонстрационный список публикаций не показывается как результат нового запроса.

## User Scenarios & Testing

### User Story 1 — Разобрать широкую нишу (P1)

Пользователь вводит широкую нишу и после загрузки видит входящие направления и слова, по которым позднее можно искать публикации.

**Acceptance Scenarios**:

1. При вводе «healthy» блок показывает несколько тематических групп с поисковыми словами, включая фитнес, питание и ЗОЖ/wellness.
2. Под блоком нет списка публикаций, если поиск ещё не подключён.

### User Story 2 — Сохранить границы узкой ниши (P1)

Пользователь вводит «фитнес и тренировки» и видит поисковые выражения только в пределах фитнеса и тренировок.

**Acceptance Scenarios**:

1. В результате присутствуют слова, связанные с фитнесом и тренировками.
2. Питание и wellness не добавляются как отдельные направления.

### User Story 3 — Получить понятную ошибку (P2)

Если сервис модели недоступен или возвращает непригодный ответ, пользователь видит ошибку и может повторить запрос. Демонстрационный разбор не подставляется вместо результата.

## Requirements

- **FR-001**: Отправлять описание ниши на сервер после нажатия кнопки, если оно непустое и не превышает 150 символов.
- **FR-002**: Получать структурированный результат с краткой общей темой и группами поисковых слов, без текстовых описаний групп.
- **FR-003**: Для широкой ниши предлагать входящие направления; для узкой не добавлять соседние темы.
- **FR-004**: Проверять ответ модели до отображения; непригодный ответ обрабатывать как ошибку.
- **FR-005**: Показывать состояние загрузки, результат и состояние ошибки в существующем блоке интерфейса.
- **FR-006**: Не отправлять ключ OpenRouter в браузер и не показывать демонстрационный список публикаций как результат живого разбора.

## Success Criteria

- **SC-001**: Пользователь видит слова, полученные именно для отправленного текста, без статического примера.
- **SC-002**: Два согласованных примера демонстрируют различие широкой и узкой ниши при живой проверке с моделью.
- **SC-003**: Пустой, слишком длинный и непригодный ответ не приводит к отображению ложного разбора.
- **SC-004**: Секретный ключ отсутствует в клиентском коде и выводимых ошибках.

## Assumptions

- Для первого прототипа модель предлагает слова на русском и английском, как было выбрано ранее для тестового поиска.
- Выбор конкретной бесплатной модели остаётся конфигурацией сервера; результат проверяется приложением независимо от модели.
- Live-проверка OpenRouter требует, чтобы пользователь добавил существующий ключ в `.env.local`.
