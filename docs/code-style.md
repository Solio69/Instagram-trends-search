# Стиль кода проекта

Этот документ описывает согласованные правила для `coding-interview`.
Перед правкой сравните их с текущим кодом и спецификацией задачи. При
рефакторинге сохраняйте поведение, DOM, HTTP-контракт и тексты, если задача
явно не требует обратного.

## Простота и границы абстракций

- Соблюдайте KISS, DRY и YAGNI: убирайте реальное повторение, но не создавайте
  слой абстракции ради единственного простого выражения.
- Применяйте SOLID там, где есть несколько обязанностей или реальная точка
  расширения. Не добавляйте интерфейсы, классы и фабрики без конкретной нужды.
- Перед новой константой или вспомогательной функцией найдите существующий
  источник значения и проверьте, подходит ли он по смыслу. Совпадение строки
  само по себе не означает одинаковый смысл.
- Общие значения контракта, статусов и заголовков держите в тематических
  модулях `app/constants/`; значения доменной логики могут находиться рядом с
  этой логикой. Значения, нужные одному компоненту, оставляйте рядом с ним.
  Пустая строка и пробел в этом проекте уже имеют общие константы в
  `app/constants/text.ts`.
- Не вводите промежуточный алиас для `HTTP_METHOD.POST` или поля
  `NICHE_API_FIELD`, если прямой доступ понятнее. Алиас допустим, когда он
  устраняет конфликт имён или сохраняет важное сужение типа.

## Данные, компоненты и JSX

- Статический объект текстов компонента (`COPY`) деструктурируйте на уровне
  модуля; данные из props и вычисляемые значения — в начале компонента или
  функции, если это не ломает сужение discriminated union в TypeScript.
- Повторяющиеся типы кнопок и полей, а также ARIA/role-атрибуты берите из
  `app/constants/dom.ts`. Статические имена классов CSS-модуля можно
  деструктурировать выше, когда это сокращает повторение; динамические
  модификаторы оставляйте индексируемыми.
- Не повторяйте длинное обращение к одному полю в выражении: извлеките значение
  один раз и дайте ему понятное имя. Для проверок состояний вычисляйте
  `isLoading`, `isReady`, `isError` до JSX.
- Многострочную разметку элементов `.map()` и условных блоков выносите в
  именованные `render...` функции выше основного `return`. Сохраняйте `key`,
  порядок элементов и условия показа. Простое однострочное выражение можно
  оставить в JSX. React hooks в render-функциях не вызывайте.
- Для выбора из конечного набора значений используйте типизированную таблицу,
  если она яснее длинной цепочки сравнений. Не меняйте запасное поведение для
  неизвестного значения.

## API, валидация и ошибки

- Повторяющиеся HTTP-методы, статусы, заголовки, роли модели и ключи API берите
  из существующих констант. Сообщения ошибок модуля группируйте в именованном
  объекте. Не объединяйте ошибки с разным назначением только из-за совпадения
  текста.
- Для проверок неизвестных значений используйте уже установленный Lodash.
  Сохраняйте точную семантику исходной проверки: например, `isString` принимает
  объектную строку, поэтому при требовании примитивной строки используйте
  проектный `isPrimitiveString` из `app/lib/type-guards.ts`.
- Числовые пределы, регулярные выражения и настройки внешнего запроса
  называйте константами, если их смысл важен для проверки или повторного
  использования. Не подменяйте значения во время чистого рефакторинга.
- Ключи внешних сервисов оставляйте на сервере и в локальном окружении;
  не выводите их в клиентский код, логи или тестовые фикстуры.

## Тесты и обязательное ревью

- Общие моковые ответы и наборы данных размещайте в `tests/fixtures/`.
  Ожидания теста для контракта задавайте независимо от констант реализации,
  иначе тест не заметит ошибочную замену значения.
- Для нового или изменённого поведения следуйте Red → Green → Refactor.
  Перестановку констант и другие изменения без поведения проверяйте
  существующими тестами и подходящими статическими проверками; не пишите тест,
  который только повторяет реализацию.
- После написания кода просмотрите **весь изменённый diff** по этому документу,
  спецификации и конституции. Проверьте существующие константы, дубли,
  деструктуризацию, JSX, ошибки, фикстуры, сохранение поведения и посторонние
  изменения. Запишите находки и исправления в `review.md` задачи.
- После исправлений повторно запустите затронутые проверки и полный
  `npm run check`. Запишите реальные команды и результаты в `verification.md`.
  Если проверка не запускалась или замечание остаётся, сообщите об этом явно.
